# ADR-0021: 前提を確かめる見本と検証用のものは、本番と同じ形で作る

## Status

Accepted

## Context

[ADR-0005](0005-designdoc-draft-checks-whole-and-mockup.md) は DesignDoc 初版の承認の前に、利用者が触る成果物の見本を作ると決めた。
成果物が届く場所があれば見本をそこに置き、そのホストの制約も確かめる。
見本や検証用のもの（ページ、スクリプト）の形（ファイルの数、モジュールの使い方、公開の仕方）は決めていない。

このテンプレートの派生先 etoyama/knowledge-enhance の Epic 1（[#2](https://github.com/etoyama/knowledge-enhance/issues/2)、2026-11-23〜27）で、
次のことが起きた。振り返り（#2 の[コメント](https://github.com/etoyama/knowledge-enhance/issues/2#issuecomment-7215229679)）と、
派生先の ADR-0014 の追記（2026-11-25）を読んで確かめた。

- 初版の前に、前提を検証した。検証の1つ（v2）ではスマートフォンからアーティファクトの db に書けるかを、1ファイルのページで確かめた。結果は通った。
- 本番の朝の画面は ES モジュールを複数のファイルに分けて公開した。S3（2026-11-25）で、このページは利用者の iPhone（iOS 18.7.3）で開けなかった。
  読み込みの後に、表示する側が「This browser isn't supported」を出した。Mac では開けた。同じ iPhone で、1枚のページ（段取りボード）は開けた。
- 公開の前にモジュールを1枚のページにつなげる形に変えると、同じ iPhone で開け、db にも書けた。原因は複数ファイルの方だった。
- 検証で通ったのは1ファイルの形で、本番の形は確かめていなかった。見落としは、Story の中で人間が実物を確かめたときに見つかった。

## Problem

- 課題1: 検証用のものの形が本番と違うと、端末やホストの差を検証で見落とす。見落とすと、Story に入ってから公開の形を作り直すことになる。
- 課題2: 検証用のものを本番と同じ形にすると、作る手間が増える。

扱わない範囲: どの端末で確かめるか（Epic ごとに違う）。見本を置く場所（ADR-0005）。

## Decision Analysis

| # | 基準 | 区分 | 分類 | 重み（決めた人） | 出典 |
|---|---|---|---|---|---|
| M1 | 検証で確かめていない形の差が、DesignDoc か ADR に書き残る | Must | - | - | 課題1 |
| W1 | 本番の形に効く端末やホストの差を、初版の承認の前に拾える | Want | 解決 | 高（人間。R1 を選んだ） | 課題1 |
| W2 | 検証の準備の手間 | Want | 費用 | 中（Claude の推測） | 課題2 |

| Must | A. 本番と同じ形で作り、変えた所は確かめていない前提として書く | B. 形は問わず、本番と違う所を確かめていない前提として書く | 何もしない |
|---|---|---|---|
| M1 | 満たす | 満たす | 満たさない（Epic 1 では1ファイルの形で通ったことだけが残った） |

| Want | A | B |
|---|---|---|
| W1 | 本番と同じ数のファイルとモジュールで開くので、Epic 1 の差は初版の前に拾えた | 差は書き残るが、拾うのは本番の形を初めて作る Story になる |
| W2 | 本番の形の分だけ手間が増える（Epic 1 では、モジュールを分けたページを1つ作る手間） | 小さい形で済む |

- 差がつく基準: W1 と W2。
- 感度: W2 を高にすると B が勝ちうる。人間が R1 を選んだので W1 を高とした。

| 案 | 起きうる悪い結果 | 抑え方 |
|---|---|---|
| A | 本番の形がまだ決まっていない | 決まっていない所は、確かめていない前提として書く |
| A | 同じ形でも、本番と違う端末で開いて差を見落とす | 本番で使う端末とホストで開く（ADR-0005 の、成果物が届く場所） |
| B | Story に入ってから公開の形を作り直す | 抑えにくい |
| 何もしない | Epic 1 と同じ見落としが起きる | なし |

## Decision

A を採る。定義の正本は [docs/WORKFLOW.md §4](../WORKFLOW.md) の2の「見本」に置き、
[.claude/rules/design-doc-template.md](../../.claude/rules/design-doc-template.md) の冒頭に1行を置く。

- 前提を確かめる見本と検証用のもの（ページ、スクリプト）は、本番と同じ形（ファイルの数、モジュールの使い方、公開の仕方）で作る。
- 本番と形を変えた所は、確かめていない前提として DesignDoc か ADR に書き戻す。

人間が R1 として選んだ（派生先の Epic 1 の振り返り、2026-11-27）。決め手は W1。

## Consequences

### Positive

- 端末やホストの差が、Story の前に見つかる。
- 検証で確かめていない形が、文書に残る。

### Negative

- 検証の準備に手間がかかる。
- 本番の形が初版の時点で決まっていないと、同じ形では作れない。そのときは確かめていない前提が残る。
- 根拠は1件（Epic 1 の iPhone）だけである。

## Alternatives considered

- **見本を全部本番のコードで作る** — 初版の前に実装を始めることになり、DesignDoc を開発しながら詳細化するフローに反する。
