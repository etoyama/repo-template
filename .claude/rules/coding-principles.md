# Coding Principles

全プロジェクト共通のコーディング原則。**YAGNI と TDD は必須**であり、プロジェクト側で
無効化しない。プロジェクト固有の規約（lint・フォーマッタ・型チェック等）は
CLAUDE.md の Tech Stack 節に書く。

## YAGNI（You Aren't Gonna Need It）

今必要でない機能・抽象・汎化を先回りで作らない。

- パターン（Repository / Factory / 抽象基底…）は必要が生じてから導入する。
  「後で要るかも」は導入理由にならない。
- 判断基準: その抽象を消しても現在の Acceptance Criteria が満たせるなら、消す。
- 共通化は同じ形が3回出てから（Rule of Three）。2回目まではコピーの方が安い。
- 設定値・拡張点・オプション引数も同じ。呼び出し側が1つしかない引数は作らない。

## TDD（t-wada 流）

テスト駆動開発は t-wada（和田卓人）が啓蒙するスタイルを標準とする。

- **Red → Green → Refactor** のサイクルを小さく回す:
  1. **Red** — 失敗するテストを1つだけ書く（コンパイルエラーも Red のうち）。
  2. **Green** — 最短で通す。仮実装（ベタ書きの定数返し）で構わない。
  3. **Refactor** — テストが緑のまま、重複除去と設計改善を行う。
- 実装を始める前に**テストリスト（TODO リスト）**を書き出し、1項目ずつ潰す。
  リストは実装中に増えてよい（気づいたら追記して今のサイクルに戻る）。
- 一般化の順序: **仮実装 → 三角測量 → 明白な実装**。いきなり一般化しない。
- テストは仕様のドキュメント。テスト名は「何がどうなるべきか」を文として書く。
- **テストコードが正（仕様）**。実装を通すためにテストを歪めない。
  テスト自体が間違っていた場合は、仕様変更としてコミットを分けて直す。

## フローとの接続

- Story の Acceptance Criteria がテストリストの種になる: AC → テストリスト → Red-Green-Refactor。
- DesignDoc の Test Design Matrix（Unit / Integration / E2E）に ✓ を付けてよいのは、
  その層のテストが Red → Green を経て存在するとき。
